# Orgnauts — Safety: the five rules the system can never skip

This page is for the Salesforce developer who is about to point Orgnauts at real orgs. It explains, in plain English,
the five hard rules the system was built around, **what mechanism enforces each one** (a rule that lives only in an
agent's instructions is a promise; the ones below are properties), and how to prove them yourself. Every mechanism named
here has a test in `test/14-hard-rules.test.mjs` that tries to break it.

The principle numbers (P1–P12) are the ones agents see in `.claude/skills/orgnauts-core-rules/SKILL.md`.

---

## Rule 1 — Production is read-only. Always.

**What it means.** No agent can change anything in production: not a record, not a field value, not a line of metadata,
not a permission. Production is used for two things only: reading data shapes (masked) and reading metadata facts. The
human deploys to production with their own tool (Blue Canvas, Gearset, `sf` — whatever they use today); Orgnauts never does.

**How it is enforced — five layers, each independent of the others.**

| Layer | Where | What it does |
|---|---|---|
| Identity | your Salesforce org | Production is reached only as a **dedicated read-only integration user** (`docs/SETUP.md §3`, recipe in `spikes/A-prod-readonly-user/`). Even a bug in Orgnauts cannot write with a user that has no write permission. Doctor #1 verifies the user's permissions. |
| Tool surface | `.claude/agents/*.md` | No agent has a production login, a deploy tool or a write tool for production. The only production tools any agent can call are `mcp__orgnauts-evidence__prod_soql / prod_row_count / prod_tooling / prod_describe` — all read-only (`readOnlyHint: true`). |
| Evidence layer | `src/engines/evidence/query.ts`, `src/mcp/evidence-server.ts` | Every production query is **parsed**: one `SELECT … FROM <object>` only — no DML keywords, no `;`, no subqueries; the object and every field must be allowlisted in `config/masking.yaml`; Email/Phone-typed fields are refused even when listed; rows are masked and capped; every call is logged to `.orgnauts/evidence.log.jsonl` with the ticket and purpose. |
| Policy hook | `src/hooks/fast.ts` (R7, R2, R1, R5, R6) | Every shell command an agent runs is checked before it executes. Any `sf` command whose target is not the configured **development** alias is denied — writes, reads, bare usernames, other sandboxes, `-o`/`--target-org` in every spelling; `sf api request` needs an explicit dev target. Since v0.3.0 (D-110) it also denies `sf` reached through a wrapper the hook cannot see into (`bash -c`, `sh -c`, `eval`, `xargs`, `env`, `node -e`, `python -c`, `npx`, an absolute path, `$(which sf)` → `R7-wrapped-sf`), any `VAR=x sf …` prefix incl. `ORGNAUTS_HOOKS_OFF=1 sf …` (`R2-env-prefix`), the human CLI by file path (`node dist/cli/human.js …`, `R1-human-verbs`) and running `orgnauts-hook` itself (`R1-hook-direct`); protected paths now include `node_modules/`, `.claude/settings.local.json`, `.gitignore`, `.forceignore`, `org/sfdx-project.json`, the Playwright auth/config files, `package-lock.json` and `tsconfig.json`, and absolute paths into the repo are judged like relative ones. Changing the default org, an alias or an auth entry (`sf config set`, `sf alias set`, `sf org login`) is denied. `HOME=`/`SF_*` overrides, direct `curl` to Salesforce and `git push` are denied. The hook fails **closed**: an internal error is a denial. **Honest framing:** this hook recognises known spellings of forbidden commands. It is a filter that catches mistakes and the obvious tricks, not a wall; a spelling nobody has thought of may pass it. The walls are the other four layers of this table, Claude Code's per-tool permission prompt, each agent's `tools:` allowlist and the fact that the only verbs with power are toolkit verbs. |
| Static belt | `.claude/settings.json`, `.claude/settings.local.json` | Claude Code's own `permissions.deny` carries the same denials for `Production*`, `UAT*`, every org in your keychain that is not the development org (regenerated by `orgnauts-human sync`), `sf org login`, `git push`, `claude`, the wrapper spellings of `sf` and of the human CLI, and the tracker's write tools by name — so even a hook that did not run would not open the door. |

**Prove it yourself.** `npm test` → test 14 "RULE 1" tries ~100 write and read commands against production, preprod, a
read-only username and an unknown sandbox and asserts every one is denied, then asserts the development alias passes.
Live: in a conductor session type `sf data query --query "SELECT Id FROM Case" -o Production` — the hook denies it with
rule id `R7-prod-soql` and the denial is recorded as a `policy.denied` event (UI → Dashboard → Safety tile).

**What is deliberately not possible.** Copying a component's body out of production into the dev sandbox. The evidence
user can tell you a class *exists* and *when it changed* (`prod_tooling`), not its source. Baseline sync copies **preprod**
into dev (P2). Opening a read path for production metadata is tracked as a future spike (`spikes/A2-prod-metadata-read/`)
and will only ever be added if it can be done with a user that has no write permission at all.

## Rule 2 — E-mail: only the addresses you listed, and delivery is contained

**What it means.** A test record, a repro script, a test class, a UI form, a draft — nothing an agent writes may carry an
e-mail address outside the list *you* maintain. And whatever the sandbox's deliverability setting, no test mail can reach a
real customer.

**Where the list lives.** `config/safety.yaml → allowed_test_emails` — edited in the UI: **⛨ Safety** screen. Entries are
exact addresses (`qa.inbox@example.com`) or patterns (`*@example.com`, `*.invalid`). Keep `*.invalid`: Salesforce
appends `.invalid` to user e-mails on sandbox refresh. The list can never be empty; junk is refused; the file is
schema-validated on every save.

**How it is enforced.**

| Mechanism | Where | What it does |
|---|---|---|
| `email-guard` gate | `src/gates/hygiene.ts` | At the end of the repro stage (and wherever the gate is listed) every file the agent touched — test data, scripts, tests, specs, artifacts — is scanned. One address outside the list fails the stage and costs the team reward points. The offender is reported masked. |
| `apex-run` scan | `src/privileged/index.ts → apexRunDev` | A repro-data script is scanned before it runs; a non-allowlisted address means it never runs. |
| `comms-lint` gate | `src/gates/hygiene.ts` | Client-visible drafts may contain **no** address at all; internal drafts only allowlisted ones. |
| Canary recipient | `runCanary` | The canary probe goes only to your own address (`ORGNAUTS_CANARY_EMAIL`), which must itself be allowlisted. |
| `data-guard` hook + `apex-run` | `src/hooks/fast.ts`, `privileged` | No data-creating tool (dev MCP write tools, anonymous Apex) runs without a **fresh** canary PASS (max age `canary_max_age_minutes`, default 30). Doctor #10 and the UI Safety screen show the age. |
| Agent instructions (P9) | core-rules skill | Agents create their own tagged records with allowlisted addresses and never act on records they did not create for the ticket. This is the one layer that is an instruction, which is why the canary exists. |

**The two delivery modes (D-102).** Sometimes a test needs a real mail to arrive, so e-mail cannot always be off. The Safety
screen offers two containment modes; the canary applies whichever you chose:

- **`blocked`** (default) — the canary sends a probe and PASSES only if the org **refuses** to send
  (`NO_SINGLE_MAIL_PERMISSION` / `NO_MASS_MAIL_PERMISSION`, i.e. Deliverability = *System email only* or *No access*).
  Safe whatever records the sandbox holds. Use it for Partial or Full Copy sandboxes, which contain real customers.
- **`allowlist_only`** — delivery may be ON. The canary then also runs an **e-mail census**: `SELECT COUNT()` of records in
  each configured field (`email_census_fields`, default `Contact.Email`, `Lead.Email`, `User.Email`, `Case.SuppliedEmail`)
  whose address does **not** match the allowlist. Any count above zero — or a field the census cannot read — FAILS the canary,
  and every data step is refused until the sandbox is scrubbed or the mode changed. Use it only for a sandbox whose
  records your team created (a Developer sandbox), because that is the only situation in which "delivery ON" can be proven safe.

**Prove it yourself.** Test 14 "RULE 2": exact entries are exact (no sibling addresses), patterns match, the canary
semantics per mode, the census SQL, the Safety screen's validation, and an `email-guard` failure on a script that carries
a customer address. Live: put a real-looking address in `work/<KEY>/artifacts/repro-data.apex` and run
`orgnauts agent gate email-guard <KEY> --stage repro`.

## Rule 3 — Nothing is guessed; every claim says where it was verified

**What it means.** An API name, a field, a row count, a platform behaviour, a test result — each one either carries a
source the human can open, or it is not in the output. "It passed" is a run file, not a sentence.

**How it is enforced.**

| Mechanism | Where | What it does |
|---|---|---|
| Contracts | `schemas/contracts/*.schema.json`, `contract-check` gate | Every stage writes a JSON contract; evidence refs must point at files that exist. A contract without evidence fails the stage. |
| Evidence layers L0–L4 | `orgnauts-evidence-contract` skill | L0 screenshot · L1 dev org retrieve/describe · L2 official docs mirror / curated note · L3 masked production query · L4 preprod (engine). Every claim names its layer and reference. |
| `plan-lint` gate | `src/gates/grounding.ts` | Every `Type.Name`-looking token in the plan — prose included — is resolved against the describe/metadata caches of your org. One name that does not exist fails the stage. A new component passes only with `action: create`. |
| `semantic-check` gate | `src/gates/grounding.ts` | No DML on non-writable fields, no edits inside managed packages, no DML/callouts in before-save flows, API version consistent with `sfdx-project.json`. |
| `assertion-referee` gate | `src/gates/verdicts.ts` | Repro: the failing test is `Fail` and the inverse `Pass` **in the toolkit's run file**. Dev/UAT: all `Pass` and the SOQL distribution assertions hold. An agent's sentence is never the verdict. |
| `unavailable ≠ passed` | `src/core/manifest.ts → stageGatesAllPassed` | A gate that could not run (missing file, crashed, unknown) is `unavailable`, and a stage with an unavailable gate does not advance — ever. |
| Honest escalation (P11) | `orgnauts-escalation-format` skill, bounce ladder | After the allowed tries, the agent writes what it gathered, what it eliminated and the exact question for the human — the toolkit escalates. A green test that proves nothing is treated as worse than an escalation. |
| Preprod parity (D-099) | `uat_verify` stage, `uat-parity` gate | "Did everything arrive in preprod?" is a fingerprint comparison between the dev source and a retrieve from preprod, not the human's memory or an agent's word. |

**Prove it yourself.** Test 14 "RULE 3", tests 04 (gates), 07 (a full ticket where QA fails and bounces on a real run file).

## Rule 4 — Knowledge comes from Salesforce documentation and vetted experts; agents never browse

**What it means.** When an agent needs to know how the platform behaves — order of execution, a governor limit, a flow
semantic — the answer comes from Salesforce's own documentation or from a note a human read and filed, with the author
named. Agents cannot search the web, so they cannot pick up a random blog post and present it as fact.

**How it is enforced.**

| Mechanism | Where | What it does |
|---|---|---|
| No web tools | every `.claude/agents/*.md` | `WebFetch` and `WebSearch` are in `disallowedTools` of all 12 agents; `npm run check:repo` (#7) fails if any agent lists them. |
| Trusted-domain mirror | `knowledge/mirror/sources.yaml → trusted_domains`, `src/engines/mirror.ts` | `orgnauts-human mirror` (a human command) fetches only from Salesforce documentation properties (developer / help / architect / trailhead / admin / engineering / release .salesforce.com and Salesforce's GitHub orgs). A source on any other host is refused and reported. Doctor #17 fails on an untrusted source. |
| Curated provenance | `knowledge/curated/*.md`, `curatedLint` | Notes by MVPs, long-time practitioners or your own architects go here, and every file must carry `source_url` (https), `author`, `trust` (`official` \| `mvp` \| `veteran` \| `internal`), `retrieved` (date) and `added_by`. `trust: official` is checked against the trusted domains. A note without provenance is flagged by doctor #17 and agents are told not to cite it (P12). |
| Citation form | core-rules skill P12, `orgnauts-plan-grounding` skill | A platform claim in a plan cites the mirror file and line or the curated note and heading (`source: L2`). `plan-lint` reads the prose. |

**Prove it yourself.** Test 14 "RULE 4": every agent file, trusted vs untrusted URLs (`medium.com`, `stackoverflow.com`,
look-alike hosts, plain `http`), curated notes with and without provenance, and the doctor failing on an untrusted mirror source.

## Rule 5 — The tracker is read-only

**What it means.** Orgnauts never writes to your ticket tracker: no comment, no status change, no assignment, no new issue.
It reads the ticket (through the Claude Code MCP connector you already use, so no API token is stored anywhere in the toolkit,
D-105) and it writes **draft** comments as files in `work/<KEY>/10-comms/` that you paste yourself.

**How it is enforced — three layers.** The `tracker-guard` hook (`src/hooks/fast.ts → decideTrackerGuard`) runs before every
tool call on the configured tracker MCP server and allows only the tools listed in `config/tracker.yaml → mcp.read_tools`; any
other tool, and any tool whose name looks like a write (add / edit / create / transition / update / delete / assign / comment /
worklog / …), is denied with rule `T1-tracker-readonly` and recorded as a `policy.denied` event. The agent `tools:` allowlists
give the tracker's read tools to **one** agent only (a1-intake) and a write tool to nobody; a tool that is not in an agent's
list cannot be called at all. And `.claude/settings.json` carries static `permissions.deny` entries for the Atlassian write tools
by name, so a hook that did not run would still not open the door. `post_draft: disabled` in `config/tracker.yaml` cannot be enabled.

**Prove it yourself.** In a conductor session ask any agent to add a comment to a ticket: the call is denied with
`T1-tracker-readonly` and appears in `work/<KEY>/events.jsonl`. Test 14 exercises the guard with read tools, write tools and
look-alike names.

## What "verified" looks like on a real ticket

For one ticket `PROJ-123`, the human can open these files and see the source of every decision:

| Question | File |
|---|---|
| What did production actually look like? | `work/PROJ-123/evidence/*.json` (masked rows, purpose, query, timestamp) and `.orgnauts/evidence.log.jsonl` |

| Does every component in the plan exist? | `work/PROJ-123/validations/plan-plan-lint.json` |

## Escape hatches — human, documented, audited

`ORGNAUTS_HOOKS_OFF=1` disables the Orgnauts hooks for one session (maintenance only); `claude --settings disableAllHooks`
disables all hooks. Neither touches the identity layer: the read-only production user and the keychain split stay in
place, so even with every hook off an agent cannot write to production. `orgnauts-human parity --accept … --reason` and
`baseline decide` are human decisions with mandatory reasons, recorded as events — they are how a human overrides a
mechanical verdict without silencing it.
